				<td colspan="3" class="article">
					<br /><div align="left">Status pages are important for maintaining a line of communication with your users in the event of a loss of services. We do this both via <a href='https://twitter.com/hackthissite' target='_new'>Twitter</a> and our <a href='https://status.hackthissite.org' target='_new'>status page</a>. Over the years we have maintained these status pages in one form or another. This varied from custom-generated output from a parsed Nagios status.dat file, to a <a href='https://cachethq.io' target='_new'>Cachet</a> site, to (currently) <a href='https://www.statuscake.com' target='_new'>StatusCake</a> pages.<br />
<br />
Through all of these iterations we always had to host this somewhere, itself a single point of failure, usually a tiny VPS with a different provider. The last and current one, StatusCake, while a cloud provider, also required a self-maintained VPS due supporting only HTTP (not HTTPS) for our status sub-domains. Some of our domains use <a href='https://en.wikipedia.org/wiki/HTTP_Strict_Transport_Security' target='_new'>HTTP Strict Transport Security (HSTS)</a>, which enforces HTTPS on all sub-domains, so their solution wouldn't work out of the box. This meant we had to run a small VPS to handle TLS certificates. Therefore, we were still stuck with pointing the status page sub-domains at a single point of failure.<br />
<br />
After years of operating this way, a recent discovery created an 'ah-ha!' moment: <a href='https://help.github.com/articles/user-organization-and-project-pages/' target='_new'>Github pages</a>. With a Github page, you can point a <a href='https://help.github.com/articles/quick-start-setting-up-a-custom-domain/' target='_new'>custom domain</a> or sub-domain to it. Earlier this year, Github added <a href='https://blog.github.com/2018-05-01-github-pages-custom-domains-https/' target='_new'>HTTPS support</a> for custom domains and sub-domains. The actual content of our status page VPS was just a couple static HTML files for frames, and a LetsEncrypt cron job, so this would work perfectly on a Github page.<br />
<br />
<div align="center"><img src='https://i.imgur.com/umWixwl.png' /><br />
<i>Screenshot of Github repository settings</i></div><br />
<br />
After following Github's directions on setting up a <a href='https://help.github.com/articles/quick-start-setting-up-a-custom-domain/' target='_new'>custom domain</a>, it just took some time until DNS propagated, Github recognized it, and offered the &quot;Enforce HTTPS&quot; option. Et voila! No more need for a VPS or single point of failure (assuming Github's pages infrastructure is resilient).<br />
<br />
The best part about this is everything included is free. StatusCake offers a rather awesome public status page setup for free, and Github pages offer an excellent way to ensure HTTPS where StatusCake cannot, also for free.<br />
<br />
You can see this in action on our status page <a href='https://github.com/HackThisSite-Status' target='_new'>Github organization</a>, or on our status pages directly:<ul><li><a href='https://status.hackthissite.org' target='_new'>https://status.hackthissite.org</a></li><li><a href='https://status.htscdn.org' target='_new'>https://status.htscdn.org</a></li><li><a href='https://status.hts.io' target='_new'>https://status.hts.io</a></li><li><a href='https://status.cryptopaste.org' target='_new'>https://status.cryptopaste.org</a></li></ul></div> <br /><br />
